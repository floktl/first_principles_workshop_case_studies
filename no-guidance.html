The Report: "The routine sometimes corrupts adjacent memory when processing long input strings."
buffer_copy.cC
void copy_input(char *dest, const char *src, int max)
{
    int i = 0;

    while (src[i] != '\0')
    {
        dest[i] = src[i];
        i++;
    }
    dest[i] = '\0';
}

The Assumption

The code assumes the destination buffer is always large enough for the source string.

The Basic Truth

C does not check lengths for you. If the copy loop ignores the provided max value, it can write past the end of dest even though the source looks valid.

The Fix Idea

"Because I know [the size limit is the only guard here], my next step is to [use max when iterating and stop before the buffer ends] instead of assuming the source length is safe."

Finding Basic Truths

Start by asking what the function can rely on. If a parameter is named max, verify whether it is actually used by the loop. If not, challenge that assumption first.

The Report: "A client message sometimes causes the parser to reject the next valid request."
protocol.cC
void process_message(int state, char *message)
{
    if (state == 0)
        handle_init(message);
    else if (state == 1)
        handle_data(message);
    else if (state == 2)
        handle_close(message);

    state++;
}

The Assumption

The parser assumes the local state variable change will persist outside the function.

The Basic Truth

In C, passing an integer by value creates a separate copy. Incrementing that copy does not alter the caller's state.

The Fix Idea

"Because I know [state is copied into the function], my next step is to [return the new state or update a state reference] rather than incrementing a local copy only."

Finding Basic Truths

Look for where values enter and exit the function. If a value is used but never returned or stored through a pointer, it may not survive the function call.

The Report: "Under load, the counter occasionally skips values and two threads appear to write the same result."
counter.cC
void increment(int *counter)
{
    int value = *counter;
    value++;
    *counter = value;
}

The Assumption

The code assumes the two read/write operations on *counter happen together as one atomic step.

The Basic Truth

Read, increment, and write are separate operations. Another thread can change *counter between the load and the store.

The Fix Idea

"Because I know [the counter is shared and not protected], my next step is to [guard the update with a lock or use an atomic increment] so the read-modify-write sequence cannot interleave."

Finding Basic Truths

Ask whether two lines rely on the same memory location. If they do, consider what else could happen between them and whether that changes the result.

The Report: "The permission system denies valid access to users. When the config sets PERMS = 0b1010, users with rights 0b1001 should pass, but they don't. The mask calculation looks correct."
permissions.cC
int check_access(int user_perms, int required)
{
    int mask = (1 << required);
    
    if ((user_perms & mask) != 0)
        return (1); // Access granted
    else
        return (0); // Access denied
}

The Assumption

The code assumes that a single bit shift (1 << required) and a single AND operation will correctly validate permissions.

The Basic Truth

required is being treated as a bit position, but in permission systems, required is usually a bitmask itself (e.g., 0b1010). The function is shifting a 1 by the entire mask value, not checking if the mask bits are present in user_perms.

The Fix Idea

"Because I know [the mask is already a bit pattern, not a position], my next step is to [AND the user_perms directly with the mask and check if ALL required bits are set], rather than [shifting a single bit by the mask value]."
