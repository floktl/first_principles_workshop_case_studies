The Report: "A long request can corrupt adjacent memory when the service copies payload into a fixed local buffer."
buffer_copy.cC
void copy_input(char *dest, const char *src, int max)
{
    int i = 0;

    while (src[i] != '\0')
    {
        dest[i] = src[i];
        i++;
    }
    dest[i] = '\0';
}

void handle_request(const char *payload)
{
    char buffer[128];
    copy_input(buffer, payload, sizeof(buffer));
    process_buffer(buffer);
}

The Assumption

The caller trusts the helper to enforce the buffer limit, but the helper ignores the only guard it receives.

The Basic Truth

max is passed into copy_input, yet the function does not use it. That means a source longer than the destination can overflow the buffer.

The Fix Idea

"Because I know [this helper owns the write into the buffer], my next step is to [stop copying when I reach max - 1 and still null-terminate dest] instead of copying the whole input blindly."

Finding Basic Truths

Identify where the buffer originates and which function must protect it. The bug is not the string contents—it is the ignored size check.

The Report: "A valid client message can leave the connection in the wrong state, causing the next request to be rejected."
protocol.cC
void process_message(int state, char *message)
{
    if (state == 0)
        handle_init(message);
    else if (state == 1)
        handle_data(message);
    else if (state == 2)
        handle_close(message);

    state++;
}

void connection_loop(void)
{
    int connection_state = 0;

    while (has_message())
    {
        char *msg = next_message();
        process_message(connection_state, msg);
        if (connection_state == 1)
            log_state("ready for data");
    }
}

The Assumption

The code assumes that incrementing the local state inside process_message will update the caller's connection state.

The Basic Truth

In C, passing an integer by value gives the function a copy. Changes to that copy do not modify the original connection_state in the loop.

The Fix Idea

"Because I know [the caller still owns the real connection state], my next step is to [return the updated state or pass a pointer/reference] so the new state persists between messages."

Finding Basic Truths

Check where the state is declared and where it is used after the call. If the function does not return it or write it back, the update is only local.

The Report: "Under load, the counter occasionally skips values and two threads appear to write the same result."
counter.cC
extern int shared_counter;

void increment(int *counter)
{
    int value = *counter;
    value++;
    *counter = value;
}

void worker(void)
{
    for (int i = 0; i < 10000; i++)
        increment(&shared_counter);
}

The Assumption

The code assumes the read-modify-write on a shared counter is atomic across multiple worker threads.

The Basic Truth

increment performs three separate operations. Another thread can change the value between the read and the write, causing lost updates.

The Fix Idea

"Because I know [the counter is shared between workers], my next step is to [guard updates with a mutex or use an atomic increment function] so the sequence cannot interleave."

Finding Basic Truths

Locate the shared resource and ask whether every access is protected. If not, the bug originates from uncoordinated access to the shared counter.

The Report: "The permission system denies valid access to users. When the config sets PERMS = 0b1010, users with rights 0b1001 should pass, but they don't. The mask calculation looks correct."
permissions.cC
int check_access(int user_perms, int required)
{
    int mask = (1 << required);

    if ((user_perms & mask) != 0)
        return (1); // Access granted
    else
        return (0); // Access denied
}

int authorize_user(int user_perms)
{
    int required = PERMS; // e.g. 0b1010
    return check_access(user_perms, required);
}

The Assumption

The code assumes required is a bit position, but the caller passes it as a full permission mask.

The Basic Truth

The caller sends PERMS as a mask like 0b1010. Shifting 1 by that value tries to access bit 10, not the bits described by the mask.

The Fix Idea

"Because I know [required is already a bitmask], my next step is to [check if user_perms contains all required bits with (user_perms & required) == required], rather than shifting a single bit by the entire mask value."

Finding Basic Truths

Trace the value from the caller to the helper. If the meaning changes along the path, the bug is in the contract between the two functions.
