The Report: "My split routine works perfectly on 'hello world', but when I test it with consecutive delimiters like 'hello world', it SegFaults and crashes instantly."
string_split.cC
int main_split_loop(char *str, char delimiter)
{
    int i = 0;
    int word_index = 0;
    
    while (str[i])
    {
        // Wait for delimiter, then copy the NEXT word immediately
        if (str[i] == delimiter)
        {
            i++; // Move past delimiter
            words[word_index] = malloc_and_copy_word(&str[i], delimiter);
            word_index++;
        }
        else
            i++;
    }
}

The Assumption

You assumed that directly after a delimiter, there is ALWAYS a valid word to copy.

STRIP: How to Find It

Ask: what does the code actually know at this moment? Then push it with an edge case. What happens after a delimiter? Is it always a character? Or could it be another delimiter? Could it be the end of string \0?

The Basic Truth

A string is just raw memory. Consecutive delimiters mean the character immediately following a delimiter might just be another delimiter, or the null terminator \0.

The Rebuild

"Because I know [delimiter runs can be longer than one char], my next step is to [advance past every delimiter until I hit a real character or the end of string] before I attempt to copy."
The Report: "My philosophers simulate fine for a few seconds, but randomly, the entire program freezes completely. Nobody eats, nobody dies, it just hangs forever."
philosophers.cC
void *philosopher_routine(void *arg)
{
    t_philo *philo = (t_philo *)arg;

    while (philo->is_alive)
    {
        // Everyone grabs their left fork first
        pthread_mutex_lock(philo->left_fork);
        
        // Then everyone grabs their right fork
        pthread_mutex_lock(philo->right_fork);
        
        eat_spaghetti(philo);
        
        pthread_mutex_unlock(philo->right_fork);
        pthread_mutex_unlock(philo->left_fork);
        
        sleep_and_think(philo);
    }
}

The Assumption

You assumed that because the code is written in order (left then right), the threads will execute cleanly and wait their turn.

STRIP: How to Find It

Ask: what must be true for this routine to work? What if all 5 philosophers acquire their left fork at the same millisecond? Then ask: what are they waiting for? Could they all be waiting for something that no one can release?

The Basic Truth

Thread execution is completely chaotic. If all 5 philosophers spawn at the exact same millisecond, they will ALL lock their left fork simultaneously. Since everyone's right fork is their neighbor's left fork, a mathematically unbreakable Circular Wait (Deadlock) occurs.

The Rebuild

"Because I know [a deadlock requires a circular wait], my next step is to [force an asymmetry into the logic (e.g. Even IDs grab Right then Left, Odd IDs grab Left then Right)], rather than [hoping the threads time themselves perfectly]."
The Report: "My shell parser uses split_string(input, '|') to break the command into pieces. It works great for ls -l | wc -l, but it completely breaks when the user types echo "hello | world" because it splits the string inside the quotes!"
parser.cC
void parse_command_line(char *input)
{
    // Assumption: The easiest way to separate piped commands
    // is to just use a simple split helper.
    
    char **commands = split_string(input, '|');
    
    int i = 0;
    while (commands[i])
    {
        execute_command(commands[i]);
        i++;
    }
}

The Assumption

You assumed that a pipe character | always means "split the command here," and that string splitting is the best way to handle parsing.

STRIP: How to Find It

Ask: what do the quotes mean? Are they just characters to be printed, or do they mean something special to the parser? When you see a | inside quotes, should it still split the command?

The Basic Truth

Quotes do not exist to be printed; they act as a boolean toggle (in_quotes = true/false). A pipe | only functions as a pipe when in_quotes == false. split_string is dumb and does not know what quotes are.

The Rebuild

"Because I know [quotes just toggle a boolean state], my next step is to [write a custom tokenizer that iterates character by character and ignores special characters when in_quotes is true], rather than [relying on a blind ft_split]."
The Report: "The allocator works perfectly on test cases, but on a large dataset with deep recursion, memory consumption grows constantly even though the tree has been deleted."
tree_allocator.cC
t_node *build_tree(int *data, int left, int right)
{
    t_node *node = malloc(sizeof(t_node));
    
    if (left > right)
        return (NULL);
    
    node->value = data[left];
    
    if (left < right)
    {
        int mid = (left + right) / 2;
        node->left = build_tree(data, left, mid - 1);
        node->right = build_tree(data, mid + 1, right);
    }
    
    return (node);
}

void delete_tree(t_node *node)
{
    if (!node)
        return ;
    
    delete_tree(node->left);
    delete_tree(node->right);
    free(node);
}

The Assumption

You assumed that the memory leak is in the delete logic, since the allocator seems to work correctly on small tests.

STRIP: How to Find It

Ask: at what point in the function does allocation happen? Does the function always allocate? What happens if you allocate memory and then return NULL? Who owns that memory if the pointer is never returned?

The Basic Truth

The leak is in build_tree. When left > right, the function returns NULL—but it already called malloc before checking. The node on the stack is orphaned and never freed. Recursive calls to deep trees mean thousands of orphaned allocations.

The Rebuild

"Because I know [malloc happens before the bounds check], my next step is to [check the bounds FIRST, before allocating], rather than allocating and then discarding the pointer."
